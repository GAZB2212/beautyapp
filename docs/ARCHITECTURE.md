# Salon App (working name) — Architecture & Data Model

A GAJO Creative product. White-label salon booking for independent hair salons and stylists.
Flat monthly fee, no marketplace, salons own their client relationships.

Status: **draft for approval** (v0.1, 2026-11-12). Nothing below is implemented yet.

---

## 1. System overview

```
                         ┌──────────────────────────────┐
  Instagram / Google /   │  apps/book  (Expo Router)     │  web: salonapp.co.uk/<slug>
  WhatsApp / QR  ──────▶ │  booking page + client app    │  iOS/Android: same code
                         └──────────────┬───────────────┘
                                        │ anon key (RLS) + Edge Functions
                         ┌──────────────▼───────────────┐
  iPad / laptop / phone  │  Supabase (London)            │  Postgres + RLS, Auth,
  ┌───────────────────┐  │  - Postgres + RLS             │  Storage (logos, photos),
  │ apps/salon        │─▶│  - Edge Functions (Deno)      │  Realtime (diary updates),
  │ dashboard (Expo)  │  │  - Storage, Realtime, pg_cron │  pg_cron (reminders, holds)
  └───────────────────┘  └───┬───────────┬───────────┬───┘
                             │           │           │
                        Stripe      Resend (email) Expo Push
                   Connect + Billing  Twilio (SMS)
```

Two Expo apps, one backend, no per-salon code. Every salon is a row in `salons`;
every tenant-owned row carries `salon_id` and Row Level Security enforces isolation.

## 2. Monorepo layout

```
salon-app/
  apps/
    book/        Expo Router. Web = public booking page (/<slug>). Native = client app.
    salon/       Expo Router. Salon dashboard: web (laptop), iPad, phone.
  packages/
    db/          Supabase CLI project: migrations, seed, generated TS types.
    core/        Shared domain logic: availability, pricing, booking rules, validation (zod).
    api/         Typed Supabase client + query/mutation helpers used by both apps.
    ui/          Shared components + brand theming (tokens from salon_branding).
    config/      tsconfig, eslint, prettier bases.
  supabase/
    functions/   Edge Functions (Deno): create-booking, stripe-webhook, stripe-connect,
                 manage-booking, process-notifications, expire-holds.
  docs/
```

Tooling: pnpm workspaces + Turborepo, TypeScript strict, Expo SDK (latest stable),
Expo Router, a shared design system in `packages/ui` (theme tokens + primitives, see
[DESIGN.md](DESIGN.md)), TanStack Query for data,
EAS for native builds, Vercel (or Cloudflare Pages) for the two web exports.

### Why two apps rather than one

The booking page must be small and fast for clients arriving from Instagram, while the
dashboard is a large authenticated app. Splitting keeps the client bundle lean, and the
client app is just `apps/book` built natively, so "same code ships to iOS, Android and web"
still holds. Shared code lives in `packages/*`.

### Web rendering trade-off (worth knowing)

Expo web is client-rendered. For speed we keep the booking bundle small and serve the
salon's public data from a single cached RPC. Link previews (Open Graph title/image for
WhatsApp and Instagram) are generated by a tiny edge function at the same URL for bot
user-agents. If Google SEO for salon pages becomes a priority later, the booking page can be
wrapped in a thin Next.js shell without changing the data layer.

## 3. Tenancy, auth and security

- **Tenant** = `salons` row. Every tenant-owned table has `salon_id uuid not null references salons`.
- **Salon users**: Supabase Auth (email + password, magic link). Membership via `salon_members`
  (`user_id`, `salon_id`, `role` in owner | manager | staff). RLS uses a `security definer`
  helper `app.is_member(salon_id, min_role)`; a user may belong to several salons (chains later).
- **Clients (v1 web)**: guest booking, no account. Name, email, mobile. They get a signed
  `manage_token` link to view/cancel/reschedule. No client data is readable with the anon key.
- **Clients (app, phase 2)**: Supabase Auth (phone OTP, Apple, Google). Their `auth.users.id`
  is linked onto `clients.user_id` by verified phone/email, so history carries over.
- **Public reads** (anon key): the anon role has no access to any table. The booking page
  reads through two functions only: `get_storefront(slug)` returns one salon's public page as
  a single JSON document (safe fields only), and `get_availability(...)` returns free start
  times. Stripe IDs, internal settings and client data never leave the database.
- **Writes from the public page** go through Edge Functions using the service role, which
  validate and apply rules server-side. The anon key cannot insert bookings directly.
- **Three layers per tenant rule**: explicit grants (column-level for writes, so fields like
  deposits, Stripe IDs and salon status are not writable from the API), RLS policies keyed on
  `app.salon_ids(min_role)`, and composite `(salon_id, id)` foreign keys plus triggers so a row
  can never reference or move to another salon.
- **Everything new is closed by default**: default API privileges are revoked for tables,
  sequences and functions, so every future table or function needs explicit grants (and
  policies) in its migration. Tests fail if a table lacks RLS or a function is callable by a
  role that is not on the allow-list.
- **Secrets live in server-only tables** (`salon_stripe`, `client_stripe`, `booking_access`,
  `stripe_events`), so Stripe identifiers and manage-link tokens cannot appear in any API
  response or realtime message.
- **Not from the API**: deleting bookings (cancel instead), deleting clients (a server-side
  owner action that also handles saved cards), changing slug/status/payment flags, creating
  salons, or accepting invites. These go through reviewed server functions.
- An independent adversarial review of the rules found no cross-salon read or write; its
  in-salon findings are fixed and covered by tests.
- **Double-booking prevention** is in the database: an exclusion constraint on
  `bookings (staff_id, during)` for live statuses, so two requests for the same slot cannot
  both succeed regardless of application code.
- Realtime (step 6): private per-salon broadcast channels fed by database triggers, rather
  than publishing tables directly, because table-level change feeds do not filter delete
  events by RLS. Nothing is published for realtime until then.

## 4. Payments

**Stripe Connect (Express)** — one connected account per salon, onboarded from the dashboard.
Deposits and no-show fees are **direct charges on the connected account**: money lands in the
salon's Stripe balance, the salon pays Stripe's processing fee, we take no application fee.

Deposit flow:
1. Client picks service → stylist → slot. `create-booking` Edge Function inserts a booking
   with `status = pending_payment` and a 10-minute `hold_expires_at`.
2. Function creates a PaymentIntent on the connected account (`Stripe-Account` header), with
   `setup_future_usage = off_session` when the salon has no-show fees enabled. Returns the
   client secret.
3. Web page renders Stripe Payment Element (Apple Pay / Google Pay / card).
4. `stripe-webhook` receives `payment_intent.succeeded` → booking `confirmed`, `payments` row
   written, confirmation notifications queued. Unpaid holds are released by `expire-holds` cron.
5. No deposit required → booking is confirmed immediately in step 1.

No-show / late-cancel fee: charged off-session against the saved payment method, only when
the salon marks the booking no-show and the salon's policy allows it. Consent text is shown
at checkout and stored (`client_payment_methods.consent_at`).

**Stripe Billing** (phase 2, modelled now): platform-level Customer per salon,
one subscription, `subscriptions` table mirrors status from webhooks. Dashboard shows a banner
when past due; booking page keeps working for a grace period.

## 5. Notifications

A `notifications` table is the queue. Rows are created on booking events (confirmation,
cancellation, staff "new booking" push) and when a booking is confirmed (reminders at 24h and
2h before, per salon setting). `pg_cron` runs every minute and calls `process-notifications`,
which sends due rows via Resend (email), Twilio (SMS) or Expo Push and records provider IDs
and failures. Templates are branded with the salon's name/logo/colour; sender is
`<Salon name> via Salon App` for email, and a shared UK SMS sender for v1.

## 6. Branding: fixed template, flexible content

`salon_branding` holds everything the booking page needs: logo, cover photo, a curated
`palette` with optional custom accent, `font_style` (one of 3 curated pairings), `layout` (classic | editorial |
minimal), tagline, about text, contact and social links, and gallery images (Storage bucket
`salon-media`, path `<salon_id>/...`). `packages/ui` turns this into theme tokens; the three
layouts are three components over the same data and the same booking flow.

QR code: generated in the dashboard (client-side), encodes `https://salonapp.co.uk/<slug>?src=qr`,
downloadable as PNG/SVG for print. Universal links / App Links are configured on the web
domain (`apple-app-site-association`, `assetlinks.json`) so the same URL opens the client app
when installed and the web page when not.

## 7. Data model (v1 tables, phase-2 tables marked ★)

All tables: `id uuid pk default gen_random_uuid()`, `created_at`, `updated_at` (trigger).
Money is integer minor units (`_pence`); `currency` defaults to GBP. Times are `timestamptz`;
each salon has a `timezone`.

### Tenancy & access
| Table | Key columns |
|---|---|
| `salons` | slug (unique, lowercase), name, status (onboarding/active/suspended), timezone (validated), currency, address fields, phone, email, stripe_charges_enabled, stripe_details_submitted, trial_ends_at. Settings, branding and Stripe rows are created automatically with each salon. |
| `salon_stripe` (server-only) | salon_id pk, stripe_account_id (Connect), stripe_customer_id (Billing) |
| `salon_settings` | salon_id pk, deposit_type (none/fixed/percent), deposit_value, cancellation_window_hours, no_show_fee_type, no_show_fee_value, slot_interval_min, min_notice_hours, max_advance_days, reminder_hours int[] (default {24,2}), allow_staff_choice, require_phone |
| `salon_hours` | salon_id, weekday (0–6), opens_at, closes_at, is_closed |
| `salon_members` | salon_id, user_id, role (owner/manager/staff), staff_id?, invited_email, accepted_at; unique (salon_id,user_id) |
| `salon_branding` | salon_id pk, logo_path, cover_path, palette (curated key), primary_color, accent_color, font_style, layout, tagline, about, instagram, facebook, tiktok, website, whatsapp, booking_message |
| `salon_gallery_images` | salon_id, storage_path, caption, sort_order |
| ★ `salon_domains` | salon_id, hostname (unique), verified_at |

### Roles

| Role | Reads | Writes |
|---|---|---|
| Public visitor | One salon's public page and free slots, via functions | Nothing directly |
| Staff | Own salon: diary, clients, services, team hours, message log | Bookings (dashboard and walk-in), blocked time, clients |
| Manager | As staff, plus the team list | As staff, plus services, stylists, hours, branding, gallery |
| Owner | As manager, plus payments, saved cards, subscription | As manager, plus salon details, booking and deposit rules (including per-service deposits), team membership |

Rules are covered by pgTAP tests in `supabase/tests/` (`scripts/test-db.sh` runs them against
plain Postgres; `supabase test db` against the full local stack).

### RPCs / Edge Functions
| Name | Where | Purpose |
|---|---|---|
| `get_storefront(slug)` | SQL function, security definer | One salon's public page as JSON: details, branding, booking rules, hours, services, stylists, gallery. Null unless the salon is live (members can preview their own). |
| `get_availability(slug, service_id, from, days, staff_id?)` | SQL function, security definer | Free start times per stylist, from staff/salon hours, blocks, live bookings (with clean-down time), unexpired payment holds, notice and advance limits. Never exposes booking rows. |
| `book_appointment(...)` | SQL function, security definer, public | Books an appointment that needs no deposit: re-checks the slot with the availability rules, finds or creates the client (never altering an existing one), queues confirmation and reminders, with per-client and per-salon limits. Refuses with `deposit_required` when a deposit is due. |
| `create_salon`, `slug_status`, `accept_invites`, `set_salon_published` | SQL functions, signed-in users | Salon sign-up, joining by invited (confirmed) email, and going live. |
| `create-booking` | Edge Function (step 5) | For bookings with a deposit: inserts a pending booking with a hold, creates the PaymentIntent on the connected account, returns the client secret. |
| `manage-booking` | Edge Function | Token-authenticated view / cancel / reschedule by client, applying the cancellation window. |
| `stripe-webhook` | Edge Function | Connect + Billing events; idempotent via `stripe_events`. |
| `stripe-connect` | Edge Function | Creates Express account, returns onboarding link, refreshes status. |
| `process-notifications` | Edge Function (cron) | Sends due rows. |
| `expire-holds` | SQL (cron) | Cancels unpaid `pending_payment` bookings past `hold_expires_at`. |

## 9. Decisions assumed (say if any are wrong)

1. Domain `salonapp.co.uk` is a placeholder; nothing hard-codes it.
2. UK first: GBP, Europe/London default timezone, Supabase London region, UK SMS sender.
3. Providers: Resend for email, Twilio for SMS, Expo Push for native push.
4. Clients book as guests in v1 (no password); accounts arrive with the client app.
5. Deposits are direct charges on the salon's connected account with no platform fee;
   the salon bears Stripe fees.
6. One service per booking in v1, data model supports several.
7. Dashboard is web-first (works on iPad Safari from day one); native dashboard build comes
   with the client app in phase 2.
